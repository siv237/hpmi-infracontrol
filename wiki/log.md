## [2026-09-04] fix | Клавиатура не работала (offset + keysym→HID)
Клавиатура в консоли не работала. Причин две, обе в `server/vnc.js`:
- **Неверные смещения в RFB-парсере.** `onKeyEvent`/`onPointerEvent` читали
  флаг/маску из `p[0]` — а это байт **типа сообщения** (`4`/`5`, всегда
  ненулевой). Правильно: `p[1]` (KeyEvent `[4][down][pad,pad][keysym u32]`,

  шлёт по RFB X11 **keysym** (напр. `a`=`0x61`, `Enter`=`0xff0d`). Добавлена
  карта `KEYSYM_TO_HID` (по эталону cryan209: `a`→4, `Enter`→40, `lctrl`→224 и
  т.д.). Shift/alt/ctrl приходят **отдельными** событиями-модификаторами, поэтому
  верхний регистр/символы мапятся на БАЗОВЫЙ (нешифтованный) ключ.
Проверено: `node --check` ОК, юнит-прогон чтения байтов (a-down/up, Enter,

## [2026-09-04] fix | Стабильность видеопотока: SequenceAck + SetEncodings
Сверка с Java-исходником (PixelBufferImage / MessageReceiverThread / LittleEndianBufferMgr):
- **`0xef SequenceNumber` — обязателен ответ-ack.** Апплет на каждый серверный
  `0xef` (3 reserved + u32 seq, LE) отвечает тем же пакетом
  (CConn.onSequenceNumber → MessageSender.sequenceNumber, writeBuffer:
  reserved+int LE). Наш клиент только читал → после ввода (рост числа кадров)
  поток мог вставать («фиолетовый экран, нет динамики»). Теперь отвечаем
  `sendCmd(0xef)` + reserved + seq LE.
- **SetEncodings (тип 2) в RFB-парсере не учитывался** → `need` оставался 4,
  noVNC-сообщение обрезалось → рассинхронизация потока. Фикс:
  `need = 4 + nenc*4` (nenc = u16 на смещении 2).
- Проверено по Java: порядок каналов HLC (blue→green→red потоки, пиксель
  `red<<16|green<<8|blue`), заголовок 12 байт при bpp>8 (совпадает с нашим
  декодером; у Java при bpp<=16 redLen не читается, но offset всё равно 12 —
  n30+=4 только при bpp>16 — у нас blueOff=12 всегда, greenOff=12+blueLen —
  для 32bpp идентично), standbyPower (зануление + инвалидейт) — совпадает.
- **Обрезка экрана снизу**: `#cvwrap` с жёстким `aspect-ratio:4/3` выталкивал
  контейнер за пределы `#screen` (main overflow:hidden) → низ резался. Фикс:
  `flex:1; min-height:0` вместо aspect-ratio — контейнер занимает доступное
  место, noVNC (`resize=remote`) вписывает канвас целиком. Проверено headless:
  overflowBy=-31px, тёмная область консоли x309-1041 y135-861 при 1400×900 —
  ничего не обрезано.
- Скриншоты переведены на `<unixtime>_<label>.png` (сортировка по числу =

## [2026-09-04] query | Диагностика лага консоли (30 с на ввод "12345")
Причина — не протокол iRMC, а серверный слой ethernet→RFB (`server/vnc.js`) +
`index.js`:
- `FramebufferUpdateRequest` (t==3) всегда слал ВЕСЬ экран raw, игнорируя
  флаг incremental; noVNC непрерывно пере-запрашивает → самоподдерживающийся
  насос полнокадровых обновлений.
- Нет backpressure: `ws.send` без контроля `bufferedAmount`; очередь росла
  бесконечно (RSS ~6.9 ГБ, +57 МБ/с). Клиент видел кадры из «минус N-секунд» —
  потому echo ввода и появлялось ~через 30 с, хотя клавиши до iRMC доходили
  мгновенно.
- Костыль после соединения из-за неверной подписи: `subscribe(cb)` вызывает
  код с `(fb, rects)`, а колбэк vnc был `(rects)` → на каждый кадр слался
  полный экран.
- `getRGB()` на 8bpp пересоздавал массив всего экрана + `convertRect`
  попиксельный: ~18-20 мс/кадр на 1024×768 + 3 МБ отправки.
- `invalidateFull()` каждые 3 с дёргал iRMC на пересылку экрана даже в простое.

Фикс в `server/vnc.js`, `server/irmc-decode.js`, `server/index.js`:
- incremental → no-op (push-модель), non-incremental → полный экран;
- коалесцинг кадров ~25 fps, кап >64 rect → весь экран;
- backpressure: при `bufferedAmount > 1 МБ` сброс очереди + pendingFull;
- `convertRect` fast-path (32bpp LE max255 shifts16/8/0) — построчный blit из
  палитры/pix без попиксельной математики (0 мс vs 10,35 мс);
- `getRGBFor(rects)` — расширение 8bpp-палитры только для dirty-прямоугольников
  с персистентным кэшем (+`paletteVer`);
- `invalidateFull` — только при отсутствии кадров >2 с.

## [2026-09-08] project | Keep-alive и восстановление сессии (надёжность)
- dmesg на тест-хосте при обрыве: `device offline error` READ + каскад
  Buffer I/O error, затем re-enum USB (`Fujitsu iRMC USB Device`). То есть
  НЕ потолок объёма: один USB-сбой → все последующие READ падают, вирт.
  CD ре-перечисляется.
- Из захвата M2 подтверждено: iRMC периодически шлёт на канал опросы-сердце —
  REQ SENSE (0x03 `03 00 00 00 12 00`), GET EVENT (0x4a `4a 01 00 00 10 00 00 08`),
  TUR (6 нулей); слой обязан отвечать им вовремя, иначе прошивка уводит
  вирт. USB в offline. Это и есть «подтверждение активности».
- Реализовано:
  * server/stor.js — мгновенный ack на 0x03/0x00/0x4a (не за READ10) +
    keep-alive: если >25с тихо от iRMC, шлём f2-подтверждение на метаканал;
  * server/m2.js — кэш lastShareCfg, watchdog (30с): если процесс M2 умер
    или сокет закрыт — пере-ишменяется share по прошлому конфигу; recover();
  * server/index.js — POST /api/mounts/recover (admin).
- Для применения живого web-сервера нужен рестарт ./start.sh (его не делал).

## [2026-09-08] lint | Скорость и «обрывы» — диагноз закрыт
- ОБРЕЗОВ НЕТ: dd bs=4M прочитал 927 MiB и продолжал; bs=1M count=512
  останавливается на 512 MiB просто потому, что count=512 есть его лимит
  (512 блоков*1M). Раньше count=600 доходил до 600MiB — подтверждено.
- Скорость ~1,7-1.0 МБ/с не зависит от bs (bs=1M/4M) и не в USB (2.0).
  Захват живого M2↔iRMC (proto_live.pcap): 26,3 READ10/с, ~38 мс/команда;
  xfer строго ЧЕРЕМУЕТСЯ: 4 сект и 60 сект, на НОВЫХ LBA без повторов.
  Малые 4-секторные — штатный паттерн инициатора iRMC, не retry. Поэтому
  ~1,7 МБ/с — это потолок таргета iRMC (USB BOT серийный + частые мелкие
  чтения), не баг нашей эмуляции и не чинится размером блока/сервером.
- Остаточный пункт надёжности: редкий transient `device offline` при тяжёлых
  чтениях + watchdog авто-воскрешает сессию (f74669d). Наблюдается не всегда.
- Что НЕ помогло бы: больший bs dd, наш сервер, keep-alive на большой объём
  (объёма-лимита нет).

  kvmToken (m_session_token/encToken), НЕ webcookie; маркер 0x00@62,
  токен с offset **63** (после put((byte)0) позиция сдвигается); 0xF2@41.

  direction=128; dataPacketLen = (dataLen+61)-32. Если слать СВОЙ header —
  BMC не принимает (повторяет команду).
