# Метрики по IPMI-over-LAN (RMCP+/UDP 623/664)

Сенсоры (температуры, кулеры) iRMC читаются **по стандартному IPMI через LAN**,
отдельным протоколом от AVR/KVM-консоли. Проверено живьём 08.09.

## Два независимых канала

- **AVR/KVM**: TCP 80, консоль/видео (`MAHOGANY KVMS LBW`, handshake `0xc8`,
  `InformVesaMode`…). Сенсоров тут НЕТ. Это то, что держит/держит сессии вьювера.
- **IPMI-LAN**: UDP **623** (RMCP) / **664** (RMCP+). Поверх — IPMI-сообщения:
  Open Session → Get Session Challenge → Activate Session → `Get SDR` /
  `Get Sensor Reading`. `ipmitool -I lanplus -H <ip> …` так и работает.
  Здесь лежат темп./кулеры питания.

## Почему вернули ф-хункц (p.5) именно так

Раньше метрики **заморозили** (решение 07.09): прежние подходы **блочили**
/мешали основной работе (держали KVM-сессии). Теперь — **интервальный опрос
по LAN**, который:
- не трогает AVR/TCP-консоль → не блокирует и не ломает KVM-сессии вьювера;
- идёт по UDP (623/664), без «удержания» соединения консоли.

## Проверено (живой iRMC S2 5.76A, `ipmitool lanplus`)

- UDP 623 и 664 на 10.67.17.101 **открыты**, RMCP+ отвечает.
- Температуры SDR: Ambient 21°C, Systemboard 38–39°C, CPU1 38–40°C, CPU2
  40–42°C, DIMM 28–38°C (пустые слоты — «No Reading»).
- Кулеры: FAN1–5 SYS **3960–4080 RPM**; FAN1–2 PSU1 6240/6360, PSU2 6480/6480.
- Итеративный опрос в Node (`server/ipmi.js`): у 10.67.17.101 10 температур +
  9 кулеров; у 10.111.17.5 (dgk24srv040) 6+14, CPU2=59°C (замечаем перегрев).

## Реализация

- `server/ipmi.js` — `readSensors({host,username,password})` → `{temps[], fans[]}`
  через `ipmitool lanplus` (UDP), парсер значения `N degrees C`/`N RPM`.
- `server/index.js` — интервальный опрос всех сохранённых серверов каждые 60 с
  (кеш `sensorCache` ключ `serverId`), неблокирующий, с пропуском перекрытий;
  `GET /api/ipmi/sensors?serverId=` (или без — все).
- Сервер при этом НЕ требует restart KVM-сессий и не держит консоль.

Смежное: AVR-протокол — `irmc-protocol.md`; проброс ISO — `irmc-storage.md`.
