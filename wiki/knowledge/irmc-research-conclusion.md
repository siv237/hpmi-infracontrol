# Заключение по исследованию монтирования ISO в iRMC (Fujitsu S2)

Результат reverse-engineering и внедрения монтирования ISO-образа в сервер
Fujitsu с BMC **iRMC S2** (протокол AVR/Avocent, `raw/avr_irmc_s2.jar`).
Исследование проведено по декомпиляции легаси (CFR), дампам сети
(`/tmp/kilo/urs2.pcap`, shim M2) и живым тестам.

## 1. Постановка

Сервис-вебка по сети монтирует ISO-образ в целевой сервер; образ появляется
как виртуальный CD-ROM (USB-транспорт) на машине `root@10.67.19.5`, BMC
которой — `10.67.17.101`. Дополнительно — контроль целостности переданного
образа и живая метрика «скорость/активность» в вебке.

## 2. Архитектура: кто что делает

Ключевой вывод: **образ отдаёт не web-клиент и не «тянет» iRMC с удалённой
шары**. Передачу исполняет **нативная библиотека M2** (`LIBM2-64.SO` на
Linux / `M2-64.dll` на Windows), лежащая в GPL-вьювере Fujitsu.

```
[web-клиент] ──HTTP── [наш сервер :1845] ──локальный сокет 5901── [движок M2]
                                                                    │ (исходящий connect)
                                          [iRMC BMC 10.67.17.101]  ──USB── [sr1 на 10.67.19.5]
```

- Наш сервер: `server/index.js` (web+API) → `server/m2.js` → `server/m2host.py`.
- `m2host.py` повторяет легаси-загрузчик `NativeInterface2`: пишет
  `StorageServer.Port=5901`, `dlopen(LIBM2-64.SO)`, ждёт `StorageServer.ActualPort`
  и держит библиотеку в потоках живой.
- M2 **сама исходящим connect** соединяется с iRMC:80 и ведёт весь диалог;
  Java/Ngu-слой общается с ней только через локальный порт 5901.
- Зависимость `libstdc++.so.5` (GCC 3 ABI) вынесена в `data/m2/lib` (система
  не тронута).

## 3. Локальный протокол Java↔M2 (127.0.0.1:5901)

Little-endian, классы `mahoganyprotocol/*`.

### Discovery (544 Б, `connectionType = 0xFE`)
```
u16 portNumber (LE) = 5901        // «StoragePort»
u8  reserved[3]
u8  connectionType = 0xFE (-2)
u8  reserved[538]
```
Ответ — 19 Б (`"00000000 …"` hex-длина по offset 9); обязателен перед share.

### Share (монтирование) — заголовок 544 Б + URSStorage 1044 Б
```
u8  reserved[5]
u8  connectionType = 0xFA (-6)
u8  reserved[538]
--- URSStorage (1044 Б) ---
u8  len0 / len1               // число UTF-16 СИМВОЛОВ пути
u8  shareType0 / shareType1   // 11 = ISO-CD, 12 = ISO-DVD ; 0xFF = UNDEFINED
u8  sharePath0[510]           // UTF-16LE, pad 0x00
u8  sharePath1[510]
u8  ipAddr[16]                // IP снабженца: ТОЛЬКО offset 0 (IPv4)!
u16 portNumber                // HTTP-порт iRMC (LE)
u8  sequence                  // 1
u8  ipType                    // 0 = IPv4
```
- **IP строго по offset 0**: иначе M2 видит `0.0.0.0` → `ECONNREFUSED`
  (`…Exception: 0xe000002c`).
- Успех share = «тишина» (M2 сама строит URS-канал); короткое окно ловит error.
- Отмонтирование — рвём сокет сессии.

## 4. Проводной протокол M2↔iRMC (то, что вскрыто)

**Бинарный вендорный фрейминг с opaque-хэндлами поверх MMC/SCSI.**

### Хендшейк
1. M2→iRMC: signature `d2 02 00 01 00 01 cd 37` (8 Б).
2. iRMC→M2: баннер `03 0a 00 00 00 00 00 00 46 75 6a 69 74 73 75 20 …` («Fujitsu …»).
3. M2→iRMC: путь к ISO в UTF-16LE (`48 00 0b ff` + путь).
4. Далее — SCSI-транзакции.

### Фрейминг
- **Два TCP-канала** к :80: основной SCSI; второй — метапоток дескрипторов
  (`00 80 f0 fa 02 …`), отвечаем подтверждением `f2 01 …`.
- Магия: **команды iRMC → `00 90 b5 09 00 10 00 00`; ответы M2 → `00 80 b5 09
  00 10 00 00`** (байт[1]=0x90/0x80 — признак направления; восстановлено живьём).
- **Длина кадра-команды = 64 + dlen**, `dlen` в [8]; CDB на offset 64
  (INQUIRY dlen=6 → кадр 70 Б).
- В заголовках — heap-указатели/хэндлы (`e3 7f 00 00`, `90 xx xx xx`);
  **iRMC их не разыменовывает** ⇒ byte-exact не требуется.
- Стартовые ответы M2 — **батч**: INQUIRY + MODE SENSE + READ CAPACITY + READ
  TOC в одном кадре (881 Б); у каждого под-ответа свой `len[8]`, idx, хэндл.

### SCSI-команды (опознаны)
`12` INQUIRY · `25` READ CAPACITY · `28` READ(10) · `43` READ TOC ·
`46` GET CONFIGURATION · `4a` GET EVENT STATUS · `51` READ DISC INFO ·
`52` READ TRACK INFO · `03` REQUEST SENSE · `22` MODE SENSE · `5a`/`0a`.

### Чистый INQUIRY-ответ (36 Б)
```
05 00 00 32 1f 00 00 00 | "Fujitsu " | "Remote Iso CDROM" | "2.04"
```
(тип 0x05 = CD, resp-fmt 0x32, addl-len 0x1f).

### Рамка данных READ10
`magic | 08 00 00 00 | idxLE | opaque | 00 04 84 00 00 02 00 00 … | idx+1 |
[секторы ISO]`.
`idx[12..15]` — дескриптор/счётчик SCSI-команд (не LBA).

## 5. Эмуляция на стороне сервера

Два рельса:

1. **Рабочий (прод)**: сервер использует **саму M2** как движок (`m2.share`).
   «Эмуляцию» выполняет библиотека; сервер лишь отдаёт путь к ISO и IP связки.
2. **Чистая Node-реализация** (`server/stor.js`, в работе): сами открываем
   канал к iRMC, проходим хендшейк, принимаем CDB и отвечаем данными из файла.
   Живьём работает хендшейк и приём INQUIRY; до полного sr1 без M2 не доведено
   (нет стартового 881-Б батча и второго канала с `f2 01`).

**Метрика «передано/скорость»**: семплирование `/proc/<m2pid>/io` `rchar`
(M2 читает ISO в том же процессе; дельта/с = реальный трафик к iRMC) →
`m2.stats()` → REST `GET /api/mounts/stats` → блок метрик в вебке.

## 6. Итоги и проверка

- **Монтирование работает**: движок M2 встроен, sr1 реально создаётся.
- **Контроль целостности**: переданный поток **побайтно равен исходному ISO**
  (sha256 совпал на тестовом образе CTRLTEST). Вирт. диск лишь прибавляет
  **один хвостовой нулевой сектор** к ёмкости — при сверке сравнивать первые
  `size_iso / 2048` секторов устройства.
- **Скорость чтения вирт. CD**: разгон ~0,3→2,8 МБ/с, стабилизация ~1,3–1,5 МБ/с.
  Подтверждено копией `dd if=/dev/sr1 of=ub.iso bs=1M count=512 status=progress`:
  512 MiB за 311,9 с = **~1,7 МБ/с** средняя. При USB 2.0 (480 Мбит/с) это ~40×
  ниже потенциала шины ⇒ узкое место — **таргет виртуального CD в iRMC**
  (задержка на команду/сектор), а не USB-транспорт.

### 6.1 Тип USB-транспорта виртуального CD (проверено живьём)
На целевой машине `10.67.19.5` виртуальный диск оформлен как **USB Mass
Storage** (драйвер `usb-storage`, интерфейс `2-6:1.0`) на USB2-шине:

- `lsusb`: `Bus 002 Device 054: ID 0000:0000 Fujitsu iRMC USB Device`
  (вирт. USB-CD с **заглушкой VID:PID `0000:0000`**, настоящих
  вендорских/девайсных ID у iRMC нет); скорость шины — **USB 2.0
  High-Speed**, `speed: 480`, `version: 2.00` (контроллер USB2 тоже 480);
- USB-путь в sysfs: `pci0000:00/0000:00:1a.7/usb2/2-6/2-6:1.0/host5/target5:0:0/5:0:0:0`
  (один LUN на `target5`);
- в `lsblk` транспорт `TRAN=usb`, `RO=0`; устройство появилось как `sr1`
  (старый пустой `sr0` — `TRAN=ata`, от прежних экспериментов с 153);
- `blockdev --getsize64 /dev/sr1` = 5183418368 Б = `getsz` 10123864 сек, т.е.
  снова **исходный 2530965 секторов + 1 нулевой сектор(2048)**.

Вывод: целевой сервер видит проброшенный образ как обычный USB CD-ROM/флешку —
никакой эмуляции на самом iRMC-хвосте не требуется (передачу ведёт M2-движок).
