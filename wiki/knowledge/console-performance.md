# Производительность консоли (bridge → noVNC)

Слой, связывающий видеопоток iRMC (Avocent "Mahogany") с браузерным VNC-клиентом
(noVNC): `server/vnc.js` (RFB 3.8 через WebSocket) + `server/index.js`
(сессии) + `server/irmc-decode.js` (палитра/фреймбуфер). Известный случай
деградации и фикс — см. `log.md` за 2026-09-04.

## Правила, чтобы не повторить лаг (30 с на ввод)

Протокол iRMC здесь не является узким местом, только серверный конвертер. Ключевые
правила:

1. **FBUpdateRequest c incremental-флагом = no-op.** Кадры push-моделью приходят
   через `subscribe(cb)` → `(fb, rects)`; не отвечать полным экраном на каждый
   re-arm-запрос noVNC.
2. **Backpressure обязателен.** `ws.send` без контроля `ws.bufferedAmount`
   копит гигабайты очереди: клиент рендерит кадры из прошлого, а ввод кажется
   зависшим на десятки секунд. При `bufferedAmount > ~1 МБ` — сбросить очередь,
   пометить `pendingFull` и переслать актуальный кадр после стока.
3. **Уведомления/создание кадров коалесцировать** (~25 fps) и сжимать dirty-регоны:
   >64 прямоугольников → слить в полный экран.
4. **Не отправлять больше того, что изменилось.** `getRGBFor(rects)` расширяет
   8bpp-палитру только для нужных регионов (кэш + `paletteVer`), а
   `convertRect` построчным blit'ом из `Buffer` (fast-path 32bpp LE max255):
   ~0 мс против ~10,35 мс на полный кадр при 1024×768.
5. **`invalidateFull` только в простое.** При активном потоке кадров он
   заставляет iRMC слать избыточный полный кадр — дёргать только когда кадров
   нет >~2 с (иначе статичный/пустой экран не приходит).

## Грабли (найдены 2026-09-04)

- Несоответствие сигнатуры колбэка: `subscribe` вызывает `(fb, rects)`, а
  первый вариант vnc-колбэка был `(rects)` → на каждый кадр уходил полный
  экран. Проверять типы аргументов при подписке.
- `Long. (8bpp)` полноэкранный `getRGB()` на каждое обновление — аллокация +
  попиксельный обход. Использовать кэш с инвалидацией по версии палитры.
