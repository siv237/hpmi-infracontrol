## 5. ✅ Графики и метрики — РАБОТАЕТ (новый метод: интервальный IPMI-LAN опрос)

> ✅ Решение владельца (08.09): метрики **восстановлены** на новом методе —
> **интервальный опрос по IPMI через LAN** (RMCP+/UDP 623/664), отдельно от
> KVM/AVR. НЕ трогает консоль → не блокирует/не ломает сессии (прежняя причина
> заморозки устранена). Детали — `knowledge/irmc-ipmi.md`.

Реализовано (`server/ipmi.js` + `server/index.js` + `web/index.html`):
- `readSensors({host,username,password})` → `{temps[], fans[]}` через
  `ipmitool lanplus` (UDP), парсер `N degrees C` / `N RPM`.
- **БД истории сенсоров** `data/metrics.json` (вне git): интервальный опрос
  всех серверов (60 с, неблокирующий) пишет ряды `[ts,value]` по каждому
  сенсору (ring-буфер ~720 точек ≈ 12ч). API: `GET /api/ipmi/sensors[?serverId=]`
  (живые), `GET /api/ipmi/metrics?serverId=` (серия + lastValues).
- Фронт: «Обзор» = дашборд ключевых состояний + сводка сенсоров (CPU/система/
  кулеры); «Оборудование» = инвентарь + полная таблица темп./кулеров.
- Сессии KVM не трогаются (только IPMI-LAN UDP) — прежний блок заморозки
  устранён. Проверено живьём (10.67.17.101: 10 темп + 9 кулеров; 10.111.17.5: CPU2=59°C).

Ранее (решение по SQLite, заморожено):

  `node:sqlite`).
- 5.2 Схема `metrics(server_id, metric, ts, value)` + индекс
  `(server_id, metric, ts)`; таблица `events` для журнала (п.12).
- 5.3 Писатель: фоновый мониторинг (п.12) — ping/response_ms каждого

- 5.4 Чтение: series, lastValues, availabilitySummary (окно),

- 5.5 Ретеншн: чистка >30 дней, запуск каждые 6ч (события — там же).
- 5.6 График доступности дашборда (п.1) работает на этих данных.

Осталось: часовые агрегатные таблицы при росте объёма (сейчас не нужно),

## 8. ✅ Дерево: редактирование и структура групп

Сейчас филиалы определяются автоматически по первым двум октетам IP, а
имя корня — из локального конфига. Нужно полноценное редактирование.
Структура хранится локально (вне git) и может быть любой: несколько
организаций-корней, вложенные группы — финальную форму владелец ещё
выбирает.

Микрозадачи:
- 8.1 **Хранение структуры**: поле `group` у сервера (servers.json, вне
  git); пусто = авто-филиал по двум октетам IP. Модал сервера: поля
  «Корень (организация)» + «Филиал / группа» с автодополнением.
- 8.2 **Контекстное меню по правой кнопке** — готово: сервер (открыть
  консоль, переименовать, переместить, удалить), группа (переименовать,
  добавить сервер, сбросить на авто-филиалы, паспорт), корень (создать
  группу, переименовать, удалить, добавить сервер), **свободное поле**
  (новая группа, новый корень, добавить сервер).
- 8.3 **Drag & drop** — готово: перетаскивание сервера в группу/корень
  (PUT /api/servers/:id {group, root}).
- 8.4 **Много корней** — готово: корни-организации (ui.json roots) +
  серверы с root='' живут в корне по умолчанию; вкладка «Группы» в
  главном меню — доска корней с группами, паспорт группы (назначение,
  адрес, ответственный, контакты, заметки), раскрытие списка серверов
  с переходом в «Серверы».
- 8.5 Связь с дашбордом (п.1): статистика по группам считается по
  структуре из 8.1.

Статус: **8.1-8.4 сделано (2026-09-09), 8.5 — план**. Структура дерева:
корни (ui.json roots + root у серверов) → группы (group у серверов +
объявления ui.json groups, в т.ч. пустые и с паспортом) → серверы
(auto-филиал по IP при пустом group).

## 10. 🔥 Проброс ISO (виртуальный диск) + сторадж ISO — план

Ключевая функция: InfraControl — хранилище ISO-образов и их проброс в
iRMC как виртуальный CD/DVD. Один образ → одновременная установка на
много серверов (режим read-only). Подключение ISO держится перманентно
и восстанавливается при потере связи.

Ресёрч легаси-кода (avr_irmc_s2.jar) — механизм выяснен окончательно
(07.09, см. wiki/knowledge/irmc-storage.md):
- Образ НЕ тянет iRMC с машины вьюера и мы ничего не слушаем. Всю
  передачу делает **нативная библиотека M2** (`LIBM2-64.so`/`M2-64.dll`,
  лежит внутри jar, класс `NativeInterface2`): она поднимает локальный
  StorageServer на `127.0.0.1:5901`, Java шлёт ей discovery (544 Б) и
  share-запрос (StorageShareRequest 0xFA + URSStorage: ip iRMC, порт,
  shareType=11 (CD-ISO), UTF-16LE-путь к ISO), а M2 сама коннектится
  к iRMC, делает handshake (signature → status → confirmation),
  открывает Storage-каналы A/B и отдаёт ISO как SCSI-таргет
  (`ScsiIsoStorageTarget`, Read10/Inquiry/... через pread64).
- Команда 153 регистрирует share (виртуальный sr0 создаётся), но без
  M2-канала данных диск остаётся пустым — наш живой тест это подтвердил.
- Весь проводной формат M2↔iRMC — внутри бинарника M2.

> ⚠ Решение владельца (07.09): полный реверс протокола M2 — задача
> сложная, **отложена в лист ожидания**.

Микрозадачи:
- 10.0a **Движок M2 встроен и РАБОТАЕТ** (08.09): `server/m2.js` + `p2host`
  (python ctypes dlopen `data/m2/LIBM2-64.so`; `libstdc++.so.5` — в
  `data/m2/lib`, вне git, скачан из archive.ubuntu, система не тронута).
  Node общается с M2 по 127.0.0.1:5901 локальным протоколом: discovery
  544 Б (0xFE) → share = заголовок 544 Б (0xFA) + URSStorage 1044 Б.
  **Подтверждено на физическом сервере**: /dev/sr1 на root@10.67.19.5 —
  iso9660, LABEL="Xubuntu 26.04 amd64", isosize=5183416320 (=размер
  образа). Реализацию 153/154 по KVM оставили, но маунт идёт через M2.
  Детали рабочего формата — в knowledge/irmc-storage.md и log.md.
- 10.0b **Лист ожидания**: потом — честный реверс протокола
  M2↔iRMC (дизассемблирование M2) и чистая реализация в Node.
- 10.1 Дописать в knowledge/irmc-protocol.md формат 153/154 (сделано
  частично; детали — в knowledge/irmc-storage.md).
- 10.2 Сторадж ISO: новая вкладка «ISO» — загрузка образов, папки,
  подписи/переименование/удаление; хранение на диске (вне git);
  HTTP-раздача read-only с инфра-сервера. **Сделано** (iso.js, вкладка
  «ISO», прогресс).
- 10.3 Протокол: реализовать 153/154 в irmc.js + storage-привилегию в
  handshake. **Сделано** (sr0 создаётся; данных нет — нужен M2-канал,
  см. 10.0a/10.0b).
- 10.4 Перманентность: «смонтированный ISO» — состояние сессии сервера;
  авто-восстановление при реконнекте (как видео), авто-отмонтирование
  при ручном отключении.
- 10.5 UI: смонтировать ISO из консоли/карточки сервера, индикация
  смонтированного образа, отмонтирование.
- 10.6 Мультиустановка: один ISO → много серверов одновременно.

Статус: **монтирование работает — подтверждено на физическом сервере

## 11. 🔥 Консольное состояние — источник истины на бэкенде — план

- 11.2 Фронт: после входа и при выборе сервера — проверять состояние; если

## 12. ⚪ Фоновый мониторинг — ОТМЕНЁН (временно)

> ⚠ Решение владельца (07.09): постоянный фоновый мониторинг из вебки
> **не делаем** — он был причиной поломок (перегруз веб-сервера iRMC →
> 503 → отваливались консоли). Код (server/monitor.js, SQLite-метрики,
> серийная очередь, приоритеты) вычищен из рабочей копии. **Позже —
> сбор по другому каналу/протоколу (не через вебку), тогда и вернём.**
> Вместо постоянного опроса — «контроль дампов»: данные снимаются и
> сохраняются только по факту подключения к серверу (см. п.4/4.1).

Ранее было:

- 12.1 Фоновый цикл: опрос всех серверов параллельно, интервал 60с
  (параметр `MONITOR_INTERVAL`).
- 12.2 События переходов → GET /api/events: «Сервер недоступен/
  доступен», «обесточен/включён», изменения конфигурации (п.6).
  Событие — только при смене статуса, повторные подавлены.
- 12.3 Метрики доступности → SQLite (п.5): ping 0/1, response_ms.
- 12.4 Last-known снимки обновляются тем же циклом (п.4) — офлайн-
  данные свежие без открытых клиентов.
- Ретеншн: чистка метрик/событий старше 30 дней (каждые 6ч).
- **Единый серийный доступ к BMC** (по требованию владельца — «коннект
  один, создаётся и переиспользуется»; требует перезапуска прода):
  - discover.js: общая очередь на хост — не больше 1 одновременного
    HTTP-обмена с каждым iRMC во всей системе (мониторинг, /api/info,
    discover, сессии KVM); параллельные digest-логины исключены;
  - один digest-логин на опрос: ретраи 5xx убраны (раньше до 5–6
    логинов на тик по больному BMC);
  - keep-alive TCP-агенты — соединение переиспользуется;
  - backoff: недоступный сервер опрашивается всё реже (x2 → x10
    интервала), доступный — каждый тик;
  - события только при смене статуса, с именем сервера; после
    рестарта процесса состояние читается из последних метрик;
  - мониторинг подключается ко всем серверам сразу при старте (2с).
  - Анти-зависание: у каждого HTTP-запроса жёсткий дедлайн (10с,
    idle 6с), задача очереди ограничена 25с — висящий запрос не может
    блокировать хост; при успехе keep-alive сокет не рвётся.
  - Приоритет полос (правило владельца): интерактив (KVM, ручные
    опросы) всегда раньше фонового мониторинга; при живой консоли
    сервера фоновый опрос этого сервера не выполняется вовсе;
    после 503 хост не трогается минимум 5 минут.
  Примечание: KVM/экран — отдельный AVR-канал iRMC (порт 590x), он
  технически не объединяется с HTTP; KVM-сессия на сервер одна и
  живёт до разрыва (п.11).
